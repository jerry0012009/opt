# 2026-09-27 回退改动审查与保留建议

## 背景

2026 年 9 月 27 日，生产环境加入了一组针对移动端滚动、会话保留、断线恢复和进程清理的改动。上线后出现了更频繁的 `Reconnecting...` 和页面重复加载现象。

当天全部未提交改动随后被回退，生产恢复至提交 `3bf1c62`（2026 年 9 月 24 日）。回退后完成了以下验证：

- 生产主页和状态接口均返回 HTTP 200。
- `codex-control.service`、`codex-ttyd.service`、`codex-tmux.service` 均正常运行，重启次数为 0。
- 独立公网 WebSocket 连续保持超过 3 分钟，2 秒心跳持续正常，没有断开。
- 回退后实际使用中没有再次出现频繁 `Reconnecting...`。

因此，本次审查遵循一个原则：**不恢复整包改动，只考虑可以独立证明价值、改动面小、不会介入连接生命周期的内容。**

## 总体建议

| 改动 | 建议 | 原因 |
| --- | --- | --- |
| Recent output 显示当前窗口编号和名称 | 可以保留 | 纯文本 UI 更新，无额外请求、定时器或进程操作 |
| View session 保留 7 天 | 简化后单独实现 | 是明确需求，但不应连带恢复其他兼容层 |
| 浏览器检测 `Reconnecting...` 并自动重载 iframe | 不恢复 | 会形成第二套重连状态机，可能放大短暂断线并造成重载循环 |
| 全局设置 tmux `alternate-screen=off` | 不恢复 | 改变所有全屏程序的终端语义，影响范围过大 |
| 根据 `alternate_on` 在 tmux 滚动和 PageUp/PageDown 间切换 | 暂不恢复 | 分支复杂，依赖应用内部行为；当前无证据表明仍需要 |
| ttyd 增加 `--signal 9` | 暂不恢复 | 属于激进清理策略；当前没有孤儿进程或客户端耗尽证据 |
| 每分钟扫描所有 view sessions 并持久化 heartbeat | 不按原实现恢复 | 功能正确但实现偏重，可降低频率并缩小状态管理范围 |

## 建议保留：Recent output 当前窗口标签

原改动将固定的 `Recent output` 更新为类似：

```text
Recent output · #5 codex
```

### 为什么安全

- 只复用状态接口已经返回的 `currentWindow` 数据。
- 不增加网络请求。
- 不增加轮询频率。
- 不操作 ttyd、WebSocket、iframe 或 tmux 会话。
- 只有少量 DOM 文本更新，性能影响可以忽略。

### 建议实现方式

只恢复以下最小逻辑：

1. 给标签增加固定 `id`。
2. 在现有 `applyStatus()` 中更新一次 `textContent`。
3. 不引入新的函数、定时器或恢复状态对象也可以完成。

这是本批回退内容中唯一适合直接重新加入的改动。

## 应当实现但需简化：View session 保留 7 天

需求是：浏览器 view session 保留 7 天；7 天内有心跳则续期；超过 7 天没有心跳且没有客户端连接时自动删除；共享主会话不能被删除。

该需求本身合理，但回退版本中的实现把以下事情同时放进了一次改动：

- 内存中的 heartbeat 节流。
- tmux option 中的持久化 heartbeat。
- 每分钟枚举全部 tmux sessions。
- 清理前再次读取状态防止竞态。
- 同时修改 alternate-screen 行为。

最后一项与生命周期完全无关，不应混在一起。每分钟扫描对于 7 天 TTL 也没有必要。

### 推荐的最小实现

1. 将默认 TTL 从 30 分钟改为 7 天。
2. heartbeat 只存储在对应 view session 的 tmux option 中，使控制服务重启后仍能识别最后活跃时间。
3. 状态接口最多每小时写一次 heartbeat。
4. 清理任务每小时运行一次，而不是每分钟运行。
5. 清理时只处理名称符合 `codex-workbench-view-<32 位十六进制 ID>` 的会话。
6. 连接中的 session 永不删除。
7. 永远不处理共享主会话 `codex-workbench`。
8. 不修改 ttyd 参数、iframe、前端定时器或 alternate-screen。

### 性能判断

按小时执行一次 tmux session 枚举，正常情况下只涉及少量会话。相比当前每 30 秒的状态接口请求，这部分开销可以忽略，也不会参与 WebSocket 数据通道。

### 发布方式

该功能应作为一个独立提交和独立部署进行验证，不应与任何滚动兼容或自动重载逻辑一起上线。

## 不建议恢复：自动重载终端 iframe

回退内容增加了一个每 5 秒执行的监控器：搜索 ttyd 页面中的 `Reconnecting...`，持续 15 秒后重载终端 iframe，并设置 60 秒冷却。

### 主要问题

- ttyd 已经自带 WebSocket 重连机制，外层页面不应再实现第二套状态机。
- 文本搜索依赖 ttyd 内部 DOM 和英文提示，属于脆弱的实现细节。
- 短暂网络切换可能被放大为 iframe 重载。
- iframe 重载会新建 ttyd 客户端和 tmux attach 进程，使日志看起来像连续重连。
- 两套重连机制可能互相打断，难以从日志区分原始断线和人为重载。

这项改动与故障时间高度相关，并且回退后问题消失，应该永久放弃。

## 不建议恢复：全局关闭 alternate screen

`alternate-screen=off` 试图让 Codex 全屏输出进入 tmux scrollback，从而继续使用 tmux copy-mode 滚动。

### 主要问题

- 它修改的是整个终端会话的行为，不只是滚动按钮。
- Codex、vim、less、top 等全屏程序都可能受到影响。
- 对已有窗口、新窗口、主会话和 view session 都要重复同步设置。
- 为兼容两种模式又需要加入 `alternate_on` 检测和两套按键路径，复杂度继续扩大。

如果未来再次出现新版 Codex 无法通过 tmux copy-mode 查看历史的问题，应先针对当前版本做实际复现，再选择单点兼容。不要预先修改所有终端程序的行为。

## 暂不恢复：ttyd `--signal 9`

该参数会在 WebSocket 关闭后直接向 ttyd 子进程发送 SIGKILL。由于子进程只是 `tmux attach-session`，理论上不会终止共享 tmux 会话，但它仍是一个更激进的生命周期策略。

当前稳定版本没有出现以下证据：

- 大量遗留 `tmux attach-session` 进程。
- ttyd 达到 `--max-clients 16`。
- 断线后的 attach 进程长期不能退出。

因此没有必要为了假设中的问题增加该参数。如果未来日志明确证明存在孤儿 attach 进程，可以把它作为单行独立改动测试，不能和重连恢复逻辑同时上线。

## 不建议恢复：应用模式滚动分支

回退内容会先检查 `#{alternate_on}`：

- alternate screen 中发送 `PageUp` / `PageDown` / `Escape`。
- 普通模式中使用 tmux copy-mode。

这会把网页按钮绑定到 Codex 当前的内部快捷键行为。Codex 更新、键位变化或其他全屏程序都可能使结果改变。当前稳定版本的滚动修复已经保留在 9 月 24 日代码中，因此没有必要额外恢复这一分支。

## 推荐执行顺序

### 第一阶段：只加入标签

- 加入 Recent output 当前窗口标签。
- 不重启 ttyd，只重启控制服务。
- 检查页面刷新、窗口切换和状态接口。

### 第二阶段：单独实现 7 天生命周期

- 使用简化的持久化 heartbeat。
- 清理频率设为每小时。
- 只重启控制服务。
- 用人工构造的过期测试 session 验证清理，不等待 7 天。
- 确认连接中的 session 和共享主会话不会被删除。

### 明确不做

- 不恢复 iframe 自动重载。
- 不恢复 `alternate-screen=off`。
- 不恢复应用模式滚动分支。
- 不在没有孤儿进程证据时加入 `--signal 9`。
- 不把多个兼容逻辑合并成一次生产发布。

## 最终结论

本批回退内容中：

- **可以直接保留的只有 Recent output 当前窗口标签。**
- **7 天 view session 生命周期值得实现，但必须拆成独立、低频、后端-only 的简化版本。**
- **其余改动目前都不值得恢复。**它们要么介入 WebSocket/iframe 生命周期，要么改变整个终端的行为，要么解决了尚未被证实的问题。

这一方案满足实际需求，同时保持生产系统的关键路径简单：浏览器连接由 ttyd 自己管理，网页不实现第二套重连机制，tmux 不承担额外的兼容层。
